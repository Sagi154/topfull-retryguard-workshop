# RetryGuard-only runs 11–18

Eight 600 s holds, TopFull off, RetryGuard on (`edge_rpr`), Paper-C1, frontend pinned at 4. Folders are `experiments/results/campaign_48/S2_sustained_overload/run_retryguard_no_topfull_sustained_overload_run11` through `run18`.

Runs 11–17 use the run 89 mix (getproduct / postcheckout / getcart / postcart / emptycart = **275 / 90 / 100 / 90 / 5**). Run 18 uses **340 / 115 / 150 / 5 / 5**, the same mix as both-off run157.

`grpc_5xx` is on the inbound CSV only for runs **16, 17, and 18**. Runs 11–15 were collected before that column existed. The controller did not read `grpc_5xx` on any of these holds.

Storefront numbers are means over `total.csv`. Failure fraction is mean `Fail` divided by mean `RPS` (`Fail` is failures per second). The rejection streak is the longest run of inbound ticks with `(Δ5xx + Δresets) / Δtotal > 0.20`. The gRPC streak uses the same bar with `Δgrpc_5xx` added to the numerator. That second streak is a reading of the CSV.

## Runs 16–18: if `grpc_5xx` were in the rejection rate

These three holds recorded `grpc_5xx` (completed gRPC codes 2, 4, 13, 14 that arrived as HTTP 200). The live controller ignored the column.

Longest streak above 0.20 if the numerator is `(Δ5xx + Δresets + Δgrpc_5xx) / Δtotal`:

| Run | Service | Streak on resets | Streak with `grpc_5xx` | Peak tick, resets | Peak tick, with `grpc_5xx` |
|---|---|---:|---:|---:|---:|
| 16 | checkout | 36 | 65 | 0.76 | 1.25 |
| 16 | recommendations | 6 | 35 | 0.38 | 1.00 |
| 17 | checkout | 34 | 41 | 0.72 | 1.23 |
| 17 | recommendations | 12 | 187 | 0.86 | 1.14 |
| 18 | checkout | 8 | 8 | 0.59 | 1.14 |
| 18 | recommendations | 14 | 292 | 0.69 | 0.91 |

A peak above 1 is the two counters stepping on each other for that tick (`Δresets + Δgrpc_5xx` larger than `Δtotal`). Checkout has 27 such ticks on run 16, 13 on run 17, and 5 on run 18. Recommendations has 0, 1, and 0. The streak length does not depend on those ticks staying under 1: a tick over 1 still counts as above 0.20.

On this reading, recommendations crosses a streak of 30 on all three holds (35, 187, 292). On resets alone it does not (6, 12, 14). Checkout's streak lengthens on runs 16 and 17 and does not move on run 18.

## Runs 16–18: retries if those gRPC completions had been retried once

Envoy did not retry these completions. The status is in the trailers of an HTTP 200, and `retryOn` is `5xx,reset,connect-failure`. Each `grpc_5xx` completion is one response that could have produced one more retry if the policy had matched it. The table adds that count once. It does not multiply by the spare attempt budget (`attempts: 3` allows two retries), and it does not guess what the follow-up call would have done.

`Δgrpc_5xx` is inbound to the service. The retry delta next to it is the frontend edge into that service, which is the only caller above 100 retries on these three holds.
