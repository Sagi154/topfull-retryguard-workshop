# S3 variant P95 (2026-10-18)

Same layout as [2026-10-18-s2-variant-p95.md](2026-10-18-s2-variant-p95.md). Each API has two tables. The both-runs table is one row per variant. The second table is one row per run.

Holds: the same 15 folders as [2026-10-18-s3-goodput-fail-rate.md](2026-10-18-s3-goodput-fail-rate.md), under `experiments/results/final_runs_results/S3_targeted_bottleneck_burst` and `S3_targeted_bottleneck_normal`. That file records all 15 clean (`health: ok`, throttle not flagged). The burst folder has no TopFull-only holds.

A run with both controllers on is counted here as TopFull only when `retryguard.log` has no `ON→OFF`. That is `analysis_s3_both_normal_run1`, `run2`, and `run3`. The three `both_burst` runs each shed (`frontend → checkoutservice`), so they stay on the both row. RetryGuard-only runs stay on their own rows. This counting is only in this file.

P95 is the Locust `Latency95` column, in ms. Mean P95 is the mean of that column on seconds with `RPS` > 0, the same seconds `analysis_score.locust_table` averages, so one run's mean matches that scorer's P95 for the API. Median P95 is the median of those same seconds. An even number of seconds uses the midpoint of the two central values.

The both-runs row gives each of its runs equal weight. With three runs, median P95 is the middle of the three run medians. The TopFull-only row has six runs, so median P95 is the midpoint of the two central run medians.
