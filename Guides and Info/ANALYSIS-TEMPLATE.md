# Analysis template

Use this when writing up one hold or a group of holds. The numbers come from `experiments/analysis_score.py`. The meanings of (a), (b), and (c) are in [2026-09-24-s2-both-off-abc-reading.md](2026-09-24-s2-both-off-abc-reading.md). The worked example of the comparison tables is [2026-10-08-s2-run24-both-on-replay-abc.md](2026-10-08-s2-run24-both-on-replay-abc.md). The worked example of the per-callee toggle table is [2026-10-09-s2-reenable-rejection-set-a.md](2026-10-09-s2-reenable-rejection-set-a.md).

`experiments/rho_estimate_report.py` is retired. Arrival rate, sojourn, and toggles come from `analysis_score.py`. Leave `rho_estimate_report.md` files that are already in run folders as they are.

`experiments/s2_both_off_abc.py` still scores the retired inbound-rejection reading. New guides use `analysis_score.py`.

## Score the folders

```powershell
python experiments/analysis_score.py <run_dir> [<run_dir> ...]
python experiments/analysis_score.py --sep 2 <run_a> <run_b> <run_c> <run_d>
```

`--sep N` inserts a bold bar (`**┃**`) after every N columns. One folder is a single-run guide: same sections, one column, no bar. Labels are the `run<N>` suffix of the folder name.

The scorer uses every inbound row and every Locust row with `RPS > 0`. It does not drop the first 30 Locust rows or the last 5 polls. Those trims belong to `s2_probe_tables.py` and the canon scorer.

The file streak is in seconds. A guide that counted consecutive rows (the four-arms file for runs 24 and 25) is a row count. Say which unit a comparison column uses. The parenthetical on a RetryGuard hold is the controller's max `high` from `retryguard.log`, which is a sample count.

## Write the guide

Put the guide in `Guides and Info/` with a date and the mix or the arm in the name. Sections, in this order. A section that does not apply (no `retryguard.log`, one hold with no replay) gets one sentence saying so.

1. **Setup.** Duration, mix as getproduct / postcheckout / getcart / postcart / emptycart, `spawn_rate`, CPU table and replica pin, which controllers are on, cool-off, folder paths.
2. **Index.** One row per arm or per generation of the same setup, with the slot numbers. Column order follows this index. A bold bar separates groups.
3. **Edge-mode bars.** Copy the scorer's first line (shed bar, climb bars, rejection bar, re-enable bar). The shed bar on that line is `rpr_threshold`. That field is the YAML key `retries_threshold`. When the START line has `burst_rpr=`, add the burst bars: `burst_rpr`, window seconds, volume floor, and the bar at each cap (`burst_rpr × attempts / attempts_on`). Locked `burst_rpr` 2.0 is 2.0 at 3 attempts, 1.33 at 2, and 0.67 at 1. `burst_rpr` 1.5 (1.5 / 1.0 / 0.5) was tried and dropped. Say that a burst shed goes to 0 and recovers on the normal path. Add the interval the hold actually used: shed and 0→1 take `interval_samples` seconds of row timestamps; 1→2 and 2→3 take `climb_interval_seconds` from the START line. Locked holds and the code default (`CLIMB_INTERVAL_SECONDS`) are 10 s. Holds that omitted the key before 2026-10-13 ran at 15 s. Holds before 2026-10-08 used 30 s for the climb steps as well as for shed and 0→1. `rpr = Δretry / (Δtotal − Δretry)` on one caller→callee edge. A tick with no first attempts is skipped and does not break the streak.
4. **(a) Edge rpr.** Three tables from the scorer, only for edges with a tick above the shed bar or a retry delta. The other controlled edges are one sentence. Cell shapes:
   - File streak seconds / ticks above the shed bar, and the controller `high` in parentheses when a log exists. **Bold** is a file streak of at least 30 seconds.
   - Mean rpr / max rpr / volume rpr. Volume is the hold's `Δretry / first attempts`.
   - Climb streaks while that attempt cap is in force: samples at 1 attempt with rpr at or under the 1→2 bar, then samples at 2 attempts with rpr at or under the 2→3 bar. An em dash means that cap never applied.
   - **4a. Burst (only when the START line has `burst_rpr=`).** A hold without it gets one sentence saying burst mode was off. Burst is a second shed test beside (a), so it never changes the (a) tables above; it adds these two:
     - **Burst window table, one row per edge that was ever at 1 or more attempts and has `burst_rpr5=` samples.** Columns: peak `burst_rpr5` / median `burst_rpr5` over that edge's `OBSERVE` lines, ticks with `burst_rpr5` at or above the bar in force (bar = `burst_rpr × attempts / attempts_on`, using that line's `attempts=`), and the burst sheds on the edge. The 20-attempt volume floor makes the controller skip a window, so a thin edge (cartservice) shows few or no samples. Say so rather than filling cells. The scorer prints it as `(a2) Burst window`, one cell per hold: `peak / median / samples at bar / burst sheds (burst_rpr5 samples)`. Paste it unchanged. It also prints a `Burst bars` line (bar at 3 / 2 / 1 attempts) that replaces the hand-written bar sentence.
     - **Burst vs normal sheds.** From the scorer's toggle table, `ON→OFF burst` is the part of `ON→OFF` fired by the burst test (`metric=rpr_burst`). Normal sheds are the difference. On a burst row of the timestamp table, `Value` is the 5 s aggregate `ΣΔretry / ΣΔfirst`, not a per-tick rpr, and `elapsed_s` is the window span, not a streak length.
5. **Rejection, beside (a).** Not the shed signal. Longest streak / count above 0.20, then longest streak / count under the re-enable bar. These are the controller's own numbers: `(Δ5xx + Δresets) / Δtotal`, plus `Δgrpc_4 + Δgrpc_14` on the four read callees (`adservice`, `currencyservice`, `productcatalogservice`, `recommendationservice`). **Bold** is a streak of at least 30 on a controlled service. Frontend and redis-cart stay plain. Two more tables (`HTTP-only rejection ... four read callees`) give the same two readings from `5xx + resets` alone, so guides written before 2026-10-13 can be compared on those four callees. Guides before 2026-10-13 show the HTTP-only number in the main table; their rescored copies end in `-rescored.md`.
6. **(b) Detector overloaded fraction.** `overloaded=1` ticks over `topfull_detect.csv` rows, as `ticks/rows (share%)`. **Bold** is a share of at least 0.5.
7. **(c) Retry volume.** Outbound retry delta by target. Inbound resets for all 11 services. The same `grpc_4 / grpc_14` pair is what the retry policy retries on, and what item 5 counts, on the four read callees.
8. **RetryGuard toggles.** Two parts, in this order. Both are required; the second summarizes the first.
   - **Part 1, per hold (the scorer's log).** One subsection per hold that has transition lines, headed by the column label from the index. Paste the scorer's count table (one row per edge or callee that toggled; columns `ON→OFF`, `0→1`, `1→2`, `2→3`) and its timestamp table (`Time (UTC)`, `Name`, `Step`, `From`, `Value`) unchanged, so every shed and re-enable is visible with its time and its rpr or rejection value. Open the section with one line saying what the `ON→OFF` and `0→1` columns mean. Holds with no transition lines are named in one sentence, not given empty subsections. Worked example: [2026-10-10-set-a-reenable-rejection-analysis.md](2026-10-10-set-a-reenable-rejection-analysis.md).
   - **Part 2, per callee.** One subsection per callee that sheds or re-enables on any hold in the group. Worked example: [2026-10-11-s2-tuning-abc.md](2026-10-11-s2-tuning-abc.md). Columns are the holds, in index order, with the same bold bars. Rows, in this order:
      - `ON→OFF / OFF→ON`, the hold's counts. When any shed on the callee was a burst shed, write `ON→OFF (burst) / OFF→ON`, for example `1 (1) / 0`.
      - Shed rpr, the `rpr` on the `ON→OFF` line. When a hold sheds more than once, list each value in time order, separated by `;`. A burst shed's value is the 5 s aggregate; tag it `b`, for example `1.62b`.
      - First shed, seconds after the first `OBSERVE` line, for the first `ON→OFF` of the hold (burst or not). Em dash when none. This row is only for guides where burst mode is on.
      - Attempts after re-enable: the attempt count that edge holds at controller exit after the 0→1 climb. A climb back through 1→2→3 is 3. A re-enable that stops at 1 is 1.
      - Time OFF, seconds from the shed timestamp to the matching `OFF→ON`, or to the `EXIT` line when the edge is still at 0. More than one OFF window: each duration in time order, separated by `;`.
      - OFF rejection min / median, three decimals, over `OBSERVE` rejection samples for that callee while the edge is at 0 attempts.
      - Streak under the bar: the longest run of those OFF-window samples strictly below that hold's `reenable_rejection`. A streak of 30 is the 0→1 step.
      An em dash means that edge never went to 0 on that hold, so the re-enable bar was not in force. A callee with no shed and no re-enable on any hold is one sentence, not a table. Under each table, two or three sentences: which holds re-enabled and how far they climbed, which stayed at 0, and the longest under-bar streak. The scorer's timestamp log is the source for the counts, the shed rpr, and the times. The OFF rejection rows are read from the log's `metric=rejection` samples inside each OFF window. The OFF rejection rows and item 5 now use the same rejection rate. Item 5 is a streak and a count. Item 8 is the minimum and the median inside each OFF window. When RetryGuard is off, say there is no `retryguard.log` and skip the tables.
9. **Locust goodput.** Mean `Goodput` while `RPS > 0`, per API.
10. **Locust fail rate.** Mean `Fail / RPS` while `RPS > 0`, per API.
11. **Locust P95.** Mean `Latency95` (ms) while `RPS > 0`, per API.
12. **Inbound arrival rate.** Positive `Δtotal` over the elapsed time of `service_inbound.csv`, per service, req/s.
13. **Inbound sojourn.** `Δrq_time_sum_ms / Δrq_time_count`, milliseconds.
14. **Share of inbound requests above 500 ms.** From the `rq_time_buckets` `le=500` cumulative count.
15. **CPU.** Per-pod quota, replica mode, mean millicores, max millicores. Mean and max are `cpu_millicores` summed across replicas, so frontend can sit above its per-pod quota.
16. **Detector max utilization.** Max `utilization` in `topfull_detect.csv` (cAdvisor CPU / per-pod quota).
17. **Throttle data quality, then TopFull live caps.** First paste the scorer's `Throttle data quality` table unchanged. A hold is **FLAGGED** when `topfull_throttle_collector.log` has any `fetch failed` WARNING (the TopFull proxy admin endpoints timed out), or when an API goes longer than 30 s without a fresh threshold or admitted read (normal is 5 s). On a flagged hold the cap and admitted-rate values are carried, not measured. Name every flagged hold in one sentence, and filter its cap and admitted-rate numbers on `threshold_fresh==1` / `admitted_fresh==1`. The rows stay in the file; the graphs draw a stale stretch as a grey band with dashed `(stale)` lines. Goodput, P95, rejection, and retry numbers do not use this file and stay valid. A flagged hold with TopFull off (`rg_only`) has no cap to lose; say so rather than dropping it. A missing `EXIT` line in `resource_usage_collector.log` is not a flag. Then the live caps: the scorer lists live reads (`threshold_fresh=1`, threshold above 0). 10000 is no cap. A live 0 is an empty read and is left out. Write the arrow trace from that list when the series is short enough to read; otherwise keep the scorer's collapsed spans. `postcart` and `emptycart` are called out when every live read is no cap.
18. **Per arm, or per hold.** One paragraph: what shed, what climbed, retry volume, `grpc_4`, and which services were detector-hot.
19. **Related links.** This template, the (a)/(b)/(c) reading, the edge-mode and burst-mode sections of [RETRYGUARD-IMPLEMENTATION.md](RETRYGUARD-IMPLEMENTATION.md), [ADR 0007](../docs/adr/0007-burst-mode-sliding-aggregate.md), and the previous guide for the same mix when one exists.

## Done when

Every section above is present or has its one-sentence omission. A hold with `burst_rpr=` on its START line has item 4a, the burst column in the count table, and `b`-tagged burst values in Part 2. A hold without it says burst mode was off. Bold marks match the rules in (a), the 0.20 rejection table, and (b). The four read callees have an HTTP-only rejection table beside the main one. Group bars match the index. The throttle data quality table is present and every flagged hold is named with how its cap and admitted-rate numbers were handled. Every hold with transition lines has its per-hold count table and timestamp log, pasted from the scorer. Each callee that sheds or re-enables has the six-row toggle table, and an edge that never went to 0 is an em dash on the re-enable rows. The file streak unit is seconds, and any column taken from an older row-count guide says so. No number in the prose disagrees with the scorer output or with `retryguard.log`.
